# 1. Lunch Forgeとは

## 1.1 プロジェクトの定義

> **Lunch Forgeは、カードを評価するAIではなく、MTGというゲームの状態変化を理解し、その結果としてシナジー・コンボ・プレイングを説明できる知識エンジンである。**

Lunch Forgeは単なるカード検索サイトではない。

カード名、色、タイプ、キーワード能力の一致だけを見て推薦するのではなく、各カードがゲーム中に起こす出来事、状態変化、条件成立、誘発、結果までを追跡する。

## 1.2 目標

Lunch Forgeの最終目標は次のとおり。

1. デッキ内の既知シナジーを説明する
2. 見落としやすい多段階シナジーを発見する
3. 理論上成立する未開拓コンボを候補として提示する
4. 推薦カードが必要な理由を具体的に説明する
5. デッキの弱点、勝ち筋、事故原因をゲーム状態から診断する
6. 将来的にマリガン、サイドボード、プレイ順まで支援する

## 1.3 非目標

初期段階では、次のことを完全自動化の前提にしない。

- 総合ルール全文を完全に再現すること
- あらゆるカード相互作用を一度に網羅すること
- 大会採用率だけでカードの強さを決めること
- AIの推測をルール上の事実として表示すること
- 色が一致するだけのカードを高シナジーとして扱うこと

# 2. 基本原則

## 2.1 色一致はシナジーではない

色、固有色、フォーマット適合は、基本的に「採用可能性を判定する制約」である。

色が一致しただけでは、原則としてシナジー点を与えない。

例外として、色を参照する能力、信心、版図、単色条件、多色条件など、色そのものがカード能力へ関係する場合のみ効果関係として評価する。

## 2.2 カード名ではなく効果を接続する

Lunch Forgeは次のような単純な関係だけに依存しない。

```text
カードA → カードB
```

中心となる表現は次のとおり。

```text
カード
  ↓
コストまたは行動
  ↓
イベント発生
  ↓
ゲーム状態変化
  ↓
条件成立
  ↓
能力誘発・適用
  ↓
新しいイベント
  ↓
結果
```

## 2.3 イベントだけでなく状態を扱う

「カードを捨てた」「土地が戦場に出た」はイベントである。

一方、次はゲーム状態である。

- パワー4以上のクリーチャーをコントロールしている
- 墓地に特定のカードがある
- 装備品が装備されている
- このターンに土地が2枚以上戦場に出た
- 手札が0枚である
- クリーチャーが死亡した回数が一定以上である

Lunch Forgeはイベントと状態の両方を保持しなければならない。

## 2.4 理論と実績を分ける

大会で使われていないことは、シナジーが存在しないことを意味しない。

以下を別の評価軸として扱う。

- ルール上の成立度
- 理論上のシナジー強度
- 再現性
- 妨害耐性
- 大会実績
- 現在のメタゲーム適性

## 2.5 説明できない高評価を出さない

高い推薦点を与える場合、Lunch Forgeは少なくとも次を説明できなければならない。

- どの効果が起点か
- 何が変化するか
- どの条件を満たすか
- 何を得るか
- 何枚必要か
- どのタイミングで成立するか
- 何に妨害されるか

# 3. Knowledge Engineの全体構造

## 3.1 三層モデル

Knowledge Engineは次の三層を基礎とする。

### 第1層：カード情報

- カード名
- Oracle ID
- 日本語名
- 英語名
- マナ・コスト
- 色・固有色
- カード・タイプ
- サブタイプ
- パワー／タフネス
- 忠誠度
- ルール文章
- 面情報
- フォーマット合法性

### 第2層：イベント

- カードを引く
- カードを捨てる
- 切削する
- 生け贄に捧げる
- 破壊する
- 追放する
- 戦場へ戻す
- 土地が戦場に出る
- クリーチャーが死亡する
- 装備する
- 攻撃する
- ダメージを与える
- カウンターを置く
- トークンを生成する

### 第3層：ゲーム状態

- `controllerHasCreature(power >= 4)`
- `cardInZone(card, graveyard)`
- `isEquipped(creature)`
- `landEnteredThisTurn >= 1`
- `graveyardCardCount >= N`
- `handSize <= N`
- `lifeTotal <= N`
- `permanentCount(type) >= N`
- `attackedThisTurn(creature)`
- `ferocious = true`
- `delirium = true`

## 3.2 状態遷移

状態遷移は、現在の状態と処理を入力し、新しい状態を出力する。

```text
S0: 初期状態
  ↓ 行動・コスト
E1: イベント発生
  ↓ 継続的効果・置換効果の適用
S1: 状態更新
  ↓ 条件確認
T1: 誘発・起動可能能力の検出
  ↓ 解決
S2: 次の状態
```

## 3.3 推奨処理順序

初期実装では、複雑性を抑えるため次の順序を採用する。

1. 採用可能性の確認
2. 能力の構造化
3. コストと結果の分離
4. イベント生成
5. 状態更新
6. 条件判定
7. 誘発候補生成
8. 結果評価
9. 説明生成
10. 信頼度表示

# 4. 用語定義

## 4.1 Event

瞬間的に発生する出来事。

例：

- `DISCARD_CARD`
- `SACRIFICE_PERMANENT`
- `LAND_ENTERED_BATTLEFIELD`
- `CREATURE_DIED`
- `BEGIN_COMBAT`
- `ATTACK_DECLARED`

## 4.2 State Fact

一定時点で真偽を持つ事実。

例：

- `HAS_CREATURE_POWER_GTE_4`
- `CARD_IS_IN_GRAVEYARD`
- `CREATURE_IS_EQUIPPED`
- `CONTROLLER_HAS_DELIRIUM`

## 4.3 Condition

能力が成立するために必要な条件。

例：

```text
zone(self) == graveyard
AND
controllerHasCreature(power >= 4)
AND
phase == beginningOfCombat
```

## 4.4 Action

ルール処理として実行する内容。

例：

- カードを1枚引く
- 対象へ3点与える
- 墓地から戦場へ戻す
- パワーを+2する
- 土地を探す

## 4.5 Cost

能力を使うために支払うもの。

例：

- マナを支払う
- カードを捨てる
- パーマネントを生け贄に捧げる
- タップする
- ライフを支払う

コストは不利益だけではない。別のカードがそのコストを利用する場合、シナジーの起点になる。

## 4.6 Trigger

特定イベントまたは状態を監視し、能力をスタックへ置く仕組み。

## 4.7 Continuous Effect

一定期間、特性またはルールを変更し続ける効果。

例：

- パワー／タフネス修整
- カード・タイプ追加
- 能力付与
- コスト軽減

## 4.8 Replacement Effect

イベントが起きる方法または結果を置き換える効果。

置換効果を無視すると、誤ったコンボを生成する可能性があるため、将来の重要要素とする。

# 6. シナジー分類

Lunch Forgeは、すべてを一つの「シナジー点」に押し込めない。

## 6.1 Synergy

効果同士が自然に価値を高め合う関係。

例：

- トークン生成 → トークン全体強化
- 切削 → 墓地参照
- カードを捨てる → マッドネス

## 6.2 Enable

別のカードの条件を成立させる関係。

例：

- パワーを4以上にする
- 墓地のカード種類を増やす
- アーティファクト数を増やす
- 土地をクリーチャー化する

## 6.3 Engine

繰り返し価値を生む関係。

例：

- 墓地と戦場を往復する
- 生け贄と再利用を反復する
- 土地を戻して再び上陸させる

## 6.4 Combo

一定の手順により、通常以上の強い結果へ到達する関係。

分類：

- 2枚コンボ
- 3枚コンボ
- 4枚以上のコンボ
- ループ
- 無限ループ
- ソフトロック
- ワンターンキル候補

## 6.5 Support

コンボ本体ではないが、成立率または継続性を高める。

例：

- サーチ
- ドロー
- 墓地回収
- 除去耐性
- マナ加速

## 6.6 Coverage

デッキの弱点を補う関係。

例：

- 横並びデッキへ全体除去耐性を追加
- 墓地依存デッキへ別軸の勝ち筋を追加

## 6.7 Meta

現在の環境に対する適性。

Meta評価はカード間のルール上の関係と分離して表示する。

# 7. シナジー判定の基本ロジック

## 7.1 Producer / Consumerモデル

各能力を「何を生み出すか」「何を必要とするか」に分解する。

### Producer

- イベントを発生させる
- 状態を作る
- 条件を満たす
- リソースを供給する

### Consumer

- イベントを参照する
- 状態を要求する
- リソースを利用する
- 条件成立時に価値を生む

基本マッチング：

```text
Producer.producesEvents
  ↔ Consumer.consumesEvents

Producer.producesStateChanges
  ↔ Consumer.consumesStates
```

## 7.2 直接接続

カードAが生成したイベントまたは状態を、カードBが直接利用する。

## 7.3 間接接続

Aが状態Xを作り、XがBの能力条件を満たし、BがイベントYを起こし、CがYを利用する。

間接接続を扱えることが、Lunch Forgeの中心的価値である。

## 7.4 負の接続

シナジーだけでなく、競合も検出する。

例：

- 同じ墓地資源を奪い合う
- 墓地を追放するカードが自分の墓地戦略を弱める
- 非クリーチャー呪文の比率を要求するカードとクリーチャー過多
- タップ能力と攻撃参加が競合する

# 8. 状態遷移グラフ

## 8.1 ノード

- Card
- Ability
- Cost
- Event
- State
- Condition
- Result
- Risk
- Evidence

## 8.2 エッジ

- `PAYS`
- `CAUSES`
- `CHANGES`
- `SATISFIES`
- `TRIGGERS`
- `ENABLES`
- `REQUIRES`
- `PREVENTS`
- `CONFLICTS_WITH`
- `RETURNS_TO`
- `SUPPORTED_BY`

## 8.3 コンボ探索

探索開始点：

- 価値の高い結果
- 現在のデッキに不足している状態
- ユーザーが選択したカード
- 特定の能力条件

探索方向：

- 前向き探索：このカードから何が起きるか
- 後ろ向き探索：この条件を何が満たせるか
- 双方向探索：起点と目標の中間経路を探す

## 8.4 探索制限

全カードを無制限に組み合わせると計算量が爆発する。

初期実装では次の制限を置く。

- 深さ上限：原則4〜6遷移
- 必要カード枚数：原則3枚まで
- 同一処理の反復回数上限
- 明確な価値増加がない経路を除外
- 合法フォーマット外を除外
- 実行不能なタイミングを除外
- 相手の協力を必要とする経路へ減点
- 既知の置換・禁止条件に反する経路を除外

# 9. シナジー評価

## 9.1 単一総合点の問題

総合点だけでは、強いが不安定なコンボと、地味だが安定したシナジーを区別できない。

Lunch Forgeでは複数軸を表示する。

## 9.2 評価軸

### Rule Validity

ルール上、本当に成立するか。

### Connection Strength

イベントと条件がどれほど直接つながるか。

### Benefit

成立したときに得る価値。

### Repeatability

繰り返し利用できるか。

### Reliability

必要カード、マナ、ターン、盤面が現実的か。

### Resilience

除去、打ち消し、墓地対策などに耐えられるか。

### Opportunity Cost

採用カードが単体でも機能するか。

### Card Count

必要枚数が多いほど原則減点する。

### Timing Complexity

フェイズ、優先権、誘発順などが厳しいほど減点する。

### Evidence

大会採用、対戦ログ、ユーザー検証などの実績。

### Novelty

既知実績が少なくても、理論上成立する新規性。

## 9.3 参考スコア構造

```text
理論シナジー点
= ルール成立度
+ 効果接続度
+ 得られる価値
+ 反復性
- 必要枚数
- マナ負担
- タイミング負担
- 妨害されやすさ

実戦補正
= 大会実績
+ 対戦ログ
+ 採用率
+ 勝率への寄与
```

最終表示では、理論点と実戦補正を混ぜず、内訳を表示する。

# 10. Explain Engine

## 10.1 目的

Explain Engineは、推薦結果を人間が確認できる形へ変換する。

## 10.2 基本出力

1. 結論
2. 起点
3. 状態変化
4. 成立条件
5. 得られる結果
6. 必要条件
7. 弱点
8. 信頼度
9. 根拠

## 10.3 表示例

```text
この3枚は「墓地利用＋条件成立＋再利用」の関係です。

1. 血茨のフレイルの装備コストで炎跡のフェニックスを捨てます。
2. 炎跡のフェニックスが墓地へ置かれます。
3. フレイルを装備した月影のパワーが合計4になります。
4. 戦闘開始時、パワー4以上のクリーチャーをコントロールしている条件を満たします。
5. 墓地の炎跡のフェニックスを戦場へ戻せます。
6. 捨てたカードを攻撃戦力として再利用できます。
```

## 10.4 必ず表示する注意

- 実際に必要なマナ
- 能力を使えるタイミング
- カードが必要な領域
- 対象の有無
- 「してもよい」か強制か
- 1ターンに1度などの制限
- 相手の妨害で途切れる場所
- ルール確認済みか推定か

## 10.5 信頼度

- **Verified:** Oracle文章とルール処理を人手確認済み
- **Parsed:** 構文解析結果に基づく
- **Inferred:** 間接推論を含む
- **Experimental:** 未検証の新規候補

# 11. ケーススタディ

## 11.1 月影＋血茨のフレイル＋炎跡のフェニックス

### 不十分な理解

```text
カードを捨てる
→ フェニックスが墓地へ
→ 墓地シナジー
→ フェニックスが戻る
```

この説明では、復帰条件が成立する理由が抜けている。

### 状態遷移としての理解

```text
血茨のフレイル
  ↓ 装備コスト
炎跡のフェニックスを捨てる
  ↓
フェニックスが墓地に存在
  ↓
フレイルを月影へ装備
  ↓ 継続的修整
月影のパワーが合計4
  ↓
「パワー4以上のクリーチャーをコントロール」の条件成立
  ↓ 戦闘開始
炎跡のフェニックスの復帰能力が利用可能
  ↓
フェニックスが戦場へ戻る
  ↓
捨てたカードを攻撃戦力として再利用
```

### 関係分類

- `Synergy`: 捨てることと墓地利用
- `Enable`: フレイルがパワー4条件を成立させる
- `Engine`: フェニックスを墓地から再利用する
- `Support`: 月影が墓地戦略を進める
- `Risk`: 装備対象除去、墓地対策、戦闘開始前の妨害

### 設計上の学び

「捨てる」と「墓地から戻る」だけを接続しても不十分。

途中の状態である `power >= 4` を追跡しなければ、正しい説明と評価はできない。

> 注：カード文章、パワー修整値、能力の正確なタイミングは実装前にOracle情報で再確認する。

## 11.2 アナグマモグラの仔＋寓話の小道

概念上の流れ：

```text
土地をクリーチャー化
  ↓
寓話の小道を生け贄
  ↓
土地を探して戦場へ
  ↓
寓話の小道を再利用可能な状態へ
  ↓
複数回の土地戦場入り
  ↓
上陸または土地参照能力を複数回利用
```

### 関係分類

- `Enable`: 土地をクリーチャーとして扱える状態を作る
- `Engine`: 土地の生け贄と再利用
- `Synergy`: 複数回の土地戦場入りと上陸
- `Risk`: 能力の対象条件、戻る領域、タップ状態、ターン制限

### 設計上の学び

「土地」「上陸」というタグ一致では足りない。

次のイベント列を理解する必要がある。

- 土地のタイプ変更
- 生け贄
- 土地サーチ
- 戦場入り
- 再利用
- 再度の戦場入り

> 注：正確なカード文章と成立手順はOracle情報で再検証する。

# 12. 未知のシナジー発見

## 12.1 既知デッキからの学習

大会デッキは、次の用途に使用する。

- 人間が発見済みの関係を収集
- 採用枚数と役割を推定
- 現実的なマナカーブを学ぶ
- シナジーが実戦で機能するか確認
- メタゲーム依存性を確認

大会採用がないことだけを理由に候補を排除しない。

## 12.2 理論探索

未知シナジーは、次の順序で探索する。

1. カード能力をイベント・状態・条件へ分解
2. ProducerとConsumerを照合
3. 直接接続を生成
4. 2段階・3段階の間接接続を探索
5. ゲーム上の利益へ到達する経路だけを残す
6. コスト、枚数、タイミング、妨害耐性を評価
7. Experimentalとして表示
8. 人間またはシミュレーションで検証

## 12.3 新規性の扱い

新規候補には、強さとは別に新規性ラベルを付ける。

- Known
- Emerging
- Uncommon
- Novel
- Unverified

# 13. データの信頼性

## 13.1 情報源

優先順位：

1. Oracleカードデータ
2. Magic総合ルール
3. 公式裁定・Gatherer rulings
4. 人手で確認した構造化データ
5. パーサー推定
6. AI推定
7. 大会・対戦ログ

ルール上の正しさと大会実績は、別種類の情報である。

## 13.2 Provenance

すべての能力解析に出所を持たせる。

```json
{
  "source": "oracle-text",
  "parserVersion": "0.1.0",
  "verifiedByHuman": false,
  "verifiedAt": null,
  "notes": []
}
```

## 13.3 誤判定対策

- 推定を事実として表示しない
- ルール確認前はExperimental
- ユーザーが誤りを報告できる
- 誤りはカード単位ではなく「解析ルール単位」で修正する
- 修正後に関連カードを再解析する
- 既知の失敗例をテストケースとして保存する

# 18. 受け入れ基準

## 18.1 両面カード

- 表面と裏面を切り替えられる
- どちらの面か分かる
- 日本語画像があれば日本語を表示する
- 日本語がなければ英語へフォールバックする
- 各面のルール文章を個別に表示する

## 18.2 シナジー推薦

- 色が同じだけのカードを上位にしない
- 推薦理由にイベントまたは状態の接続を含める
- 関係分類を表示する
- 2枚以上の関係を説明できる
- 不確実な推論へラベルを付ける

## 18.3 ケーススタディ

月影＋血茨のフレイル＋炎跡のフェニックスについて、少なくとも次を説明できる。

- フェニックスを捨てる
- フェニックスが墓地にある
- 月影へフレイルを装備する
- 月影のパワーが4になる
- フェニックスの条件を満たす
- 戦闘開始時に復帰する
- 妨害される箇所

## 18.4 Explain

- 「なぜこのカードか」に答える
- 起点から結果まで順序表示する
- 省略した前提を明示する
- 信頼度を表示する
- ルール未検証の場合は断定しない

# 22. 開発判断のチェック質問

- 条件成立の途中段階を省略していないか

# 23. 最終方針

Lunch Forgeの競争力は、カードデータの量だけでは生まれない。

重要なのは、カードが作るイベント、変化したゲーム状態、成立する条件、次に発生する能力を連鎖として理解することである。

```text
カード
  ↓
コスト・行動
  ↓
イベント
  ↓
状態変化
  ↓
条件成立
  ↓
能力
  ↓
結果
  ↓
説明
```

この構造を中心に開発する。

大会データは答えそのものではなく、理論上の評価を実戦から補正する材料として使う。

AIは根拠のない知識を作るのではなく、構造化された知識を探索し、候補を提示し、説明し、検証を助ける役割を担う。
